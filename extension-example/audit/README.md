# 审计日志插件示例

在 `log` 阶段记录网关上每一次写请求：谁、什么路径、什么状态码、什么时候。它不拦截任何东西 —— 响应早已发出，它只是把发生过的事记下来。

三个示例覆盖三种形态：[`notes`](../notes) 是目的地（自己的 API 和页面），[`ratelimit`](../ratelimit) 是关卡（拦在所有人前面），这个是记录者。

```
CGO_ENABLED=0 go build -o bin/plugin .
```

## 它的来历

这份代码最初是一次实验的产物：交给一个**只被允许读 `docs/plugin-development.md`** 的作者，看他会在哪里卡住。他写出来的东西编译不过，而每一处失败都精确对应指南的一个缺口 —— 查询构造器只文档化了一半、比较值必须是字符串这件事没写、日志字段的类型限制没写、`FilterRequest` 有哪些字段完全没列。

最要命的一处是：指南的**第一个示例**教的是 `sdk.User(r.Context()).Username`，而 `User` 在匿名请求上返回 `nil` —— 那行代码会 panic，而插件里的 panic 会杀掉进程。他毫不犹豫地把这个模式抄进了自己的插件。

那些缺口都补上了，这份代码也改成了正确的写法。留着它作为示例，是因为它是照着文档能写出来的东西，而不是照着源码。

## 三处值得看的

**审计不是免费的完整。**

`log` 阶段是 fail-open 的：filter 失败时请求照常成功，而这条审计记录就没了。插件崩了、熔断开了、正在排空、数据库正在重启 —— 这些时候写请求都会通过，但没有记录。

**但这次丢失不是静默的。**Core 会报出来，带着插件名和 filter 名（实测 `tests/audit_loss_test.go`）：

```
auditor/access-log: plugin is not running
```

这个区别决定了运维该做什么：审计日志的空洞是**可数的**。给 filter 错误配告警，就能知道缺了多少、缺在哪段时间 —— 而不是拿到一份看起来完整、实则不知道漏了什么的记录。一份有已知空洞的审计，比一份不知道有没有空洞的强得多。

一个叫「审计日志」的东西默认是尽力而为的，这一点必须知道。真要保证完整，就在 `log` 阶段里把记录投进持久队列（那里有至少一次投递保证），用一点延迟换不丢 —— 但注意这只是把窗口缩小：投递本身也在同一个 fail-open 的 filter 里，插件整个不在的时候一样投不进去。真正的「一条都不能少」需要在 Core 里做，不是在插件里。

好消息是它没有盲区的另一半：`log` 阶段对**每个**请求都跑，包括被更早的 filter 短路的、鉴权失败的、后端返回 5xx 的。被拒绝的流量同样会被记下来。

**菜单上的 `roles` 不保护这条路由。**

```go
if !sdk.User(r.Context()).HasRole("admin") {
    http.Error(w, "forbidden", http.StatusForbidden)
    return
}
```

manifest 里 `menus[].roles: [admin]` 只决定这个菜单项显示给谁 —— 任何知道 URL 的人都能直接请求 `/api/plugins/audit/entries`。鉴权必须在 handler 里做。这个示例最初就是漏了这一步，交付了一个所有人可读的审计日志。

**读调用者要用 nil 安全的方法。**

`sdk.User(ctx)` 在没有登录用户时返回 `nil`，所以用 `.Name()` / `.ID()` / `.HasRole()`，不要直接取字段。插件里的 panic 不是 500，是进程死亡 —— 一个未登录的请求就能让审计停摆。

## 保留期

```yaml
config:
  - key: retention_days
    type: int
    default: "30"
```

声明在 manifest 里，所以控制台按声明渲染表单、Core 把默认值补给插件、审核的人能看到它可以被配置成什么。改动立即推送到运行中的进程，不需要重启。

清理由一个定时任务做，用 `job.Scheduled`（这次运行本该发生的时刻）而不是 `time.Now()` 计算截止时间 —— 任务晚跑十分钟不该让保留边界跟着挪十分钟。

时间字段存成 RFC3339 字符串而不是 unix 整数：比较值一律是字符串，字典序必须等于时间序，`Lt` 才能正确筛出过期记录。
