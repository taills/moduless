# 库存插件示例

围绕**事务**的例子。另外三个覆盖三种形态 —— [`notes`](../notes) 是目的地、[`ratelimit`](../ratelimit) 是关卡、[`audit`](../audit) 是记录者 —— 这个覆盖的是「不用事务就得不到正确答案」的场景：预留库存。读取余量、做判断、写回扣减，必须是同一个不可分割的动作，否则两个顾客都看到最后一件，也都拿到了。

```
CGO_ENABLED=0 go build -o bin/plugin .
```

## 它测出来的东西

这份代码不是照着文档写完就完了，是**真的跑过并发**才成型的。同一个场景（10 件库存，30 个并发预留）跑了三次：

| 版本 | 卖出 (201) | 拒绝 (409) | 服务器错误 (500) |
|---|---|---|---|
| 不重试 | 2 | 0 | 28 |
| 只重试版本冲突 | 10 | 0 | 20 |
| 重试冲突 + 重试限额 | **10** | **20** | **0** |

三次的库存始终没被超卖 —— 但前两次里，一个能正常工作的系统对外表现得像坏了。

## 三处值得看的

**事务保证的是原子，不是不争抢。**

```go
found, version, err := tx.Get(ctx, "items", sku, &item)
...
tx.PutIfVersion(ctx, "items", sku, item, version)
```

两个事务都能读到同一行。第二个写入会被**拒绝**（而不是被允许覆盖掉第一个），所以 `sdk.ErrVersionConflict` 是竞争下的**正常结果**，不是故障。把它当错误报出去，一个热门商品就变成一堵 500 的墙 —— 第一版就是这样，30 个请求卖出 2 件。

正确做法是重试整个事务，而不是重试那一次写：余量已经变了，判断必须重做。

**事务名额是有限的，撞上要退避。**

一个事务会占住一条数据库连接，所以 Core 限制单个插件同时能持有几个（`MaxOpenTxPerPlugin`，默认 4）。撞上限额返回 `sdk.ErrRateLimited` —— 这是「现在很忙」，不是「坏了」，同样要退避重试。

这一条是实测才发现的，而且顺带发现了 Core 自己的一个 bug：限额的检查和登记不在同一把锁里，30 个并发请求全都数到 0、全都通过了上限为 4 的检查，实际打开了 17 个 —— 连接池一共才 25 条。那个上限存在的理由，恰恰在它最该生效的时刻失效了。现在修好了，日志里能看到它精确停在 4。

**不是所有写都需要事务。**

`restock` 只改一个文档，用 `PutIfVersion` 加重试就够了。事务是给「两个文档必须一起变」准备的，不是每次写都套上。

## 提交之后才做的事

```go
if remaining <= lowStockAt() {
    log.Printf("low stock: %s down to %d", sku, remaining)
}
```

低库存告警在事务外面。放进去的话，一个后来回滚掉的预留也会发出告警 —— 而告警是收不回来的。

## 它需要什么

```yaml
permissions:
  - db
  - db:tx
```

`db:tx` 和 `db` 是分开的，因为一个开着的事务会占住连接直到结束，比单条语句重得多。只读写文档的插件不该申请它。
