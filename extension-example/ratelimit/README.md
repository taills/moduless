# 限流插件示例

一个纯 filter 插件：不拥有路由、不拥有数据表、不拥有菜单，只坐在**所有人**的请求前面，决定它是否可以继续。

这是 IIS Filter 模式最纯粹的形态。另一个示例 `../plugin/`（notes）展示的是插件作为「目的地」——有自己的 API、表和界面；这个展示的是插件作为「阶段」。两者组合起来才是完整的插件模型。

```
CGO_ENABLED=0 go build -o bin/ratelimit .
```

## 它证明了什么

| 能力 | 体现在 |
|---|---|
| 一个插件能治理**另一个**插件的路由 | `match.paths: ["/**"]`，限流对 `/api/plugins/notes/*` 同样生效 |
| 零权限插件 | `permissions: []`——审批的人一眼看到它碰不到数据库、队列、文件和网络 |
| 配置热推送 | `OnConfigChanged` 在启动时和每次变更时各调用一次，改限流阈值不需要重启 |
| fail-open 的正确用法 | 限流器挂了不该拒绝所有流量，见下 |

对应的实测在 `tests/example_ratelimit_test.go`——它按真实分发布局（manifest + bin/）安装这个插件，再打真实 HTTP 流量。

## 三个值得解释的决定

**为什么 `fail_closed: false`。** 限流器是防过载的，它自身故障不是安全事件。如果限流插件崩了就拒绝全站流量，等于把一次小故障放大成全面中断。反过来，WAF 或鉴权 filter 必须 `fail_closed: true`，并接受「自己挂了全站就挂」——因为它们的绕过才是真正的损失。

**为什么 `order: 1`。** 会被拒绝的请求应该在任何其他插件为它花费成本之前就被拒绝。限流器排在最前面。

**为什么 `replicas: 1`。** 令牌桶存在进程内存里，两个副本各自放行完整速率，实际限流就翻倍了。要做多副本，把计数移到 host 的缓存能力上（`permissions: [cache]`，用 `sdk.Cache` 做原子递增），代价是每个请求多一次跨进程调用——对限流器这种「每个请求都要过」的组件来说，这个代价需要先测再决定。

## 配置项

在控制台的插件配置里设置，保存后立即生效：

| 键 | 默认 | 说明 |
|---|---|---|
| `requests_per_minute` | 100 | 每个调用方的稳态速率 |
| `burst` | 20 | 突发容量，也是空闲后可攒的上限 |
| `exempt_paths` | 空 | 逗号分隔的前缀，命中则不限流 |

无法解析的值回落到默认值，而不是关闭限流——否则控制台上的一个笔误就变成一扇敞开的门。

调用方的划分：已登录用户按 user id 计（同一个人开多个标签页算一份预算），未登录按来源 IP 计（在鉴权阶段之前，这是能拿到的最好身份）。

## 观察它

```
GET /api/plugins/ratelimit/stats
```

这个路径**永远不被限流**，代码和 manifest 两处都保证了。站点被打的时候，最不该丢的就是那个能解释「为什么在被打」的页面。
